# Short detailed windows

**Analyze a short window** or `hogline window SOURCE_ID --start 1800 --end 1820 --interval 0.5` enqueues a durable detailed job. The existing local worker claims it with a lease and bounded retries. No game or end record is created automatically.

The decoder seeks once and processes at most 60 source seconds, 240 selected frames, and 120 decoder wall seconds. Sample intervals range from 0.25 to 2 seconds, defaulting to 0.5. Samples use a grid anchored to the original source timeline, rather than repeatedly waiting a minimum interval after the previous selection. Each bucket keeps its first available native frame; a partial initial bucket is skipped. A 0.25-second request at 30 fps alternates seven/eight native-frame steps instead of drifting to 0.267 seconds per sample. Overlapping windows with nested cadences share original frames when present. A request containing no grid target is rejected. Original integer PTS and rational timebases come from FFmpeg's [showinfo](https://ffmpeg.org/ffmpeg-filters.html#showinfo); the [select filter](https://ffmpeg.org/ffmpeg-filters.html#select_002c-aselect) chooses frames without replacing timestamps or manufacturing a constant frame rate. Variable-frame-rate gaps and nonzero local start timestamps have integration tests. The source origin is subtracted only inside the selection expression; emitted PTS stay unchanged. Decoder version `original-pts-source-grid-v2` pins the new selection semantics so old cached windows cannot substitute for new work.

The worker-time limit defaults to 120 seconds including media resolution, decoding, detection, and publication. An in-progress media resolver can take up to its existing 60-second timeout to return; decoder ticks check cancellation, leases, and elapsed time. Closing an interrupted decoder kills and reaps the child process. Retained data defaults to 64 MiB per window; PNG anchors and Parquet count against this and the shared cache limit. These limits do not measure downloaded network bytes. Remote seeks may fetch surrounding codec/keyframe data.

## Stored observations and evidence

Each selected frame produces one [Parquet](https://arrow.apache.org/docs/python/parquet/parquet.html) row per overhead view. Explicit column types retain original PTS/timebases, source/manifest/profile/model hashes, source-relative time, YouTube timestamp link, decoded RGB hash, crop dimensions, handle centers/colors/shapes, motion, and large dark regions. The file metadata embeds the pinned job inputs. Coordinates are crop pixels, with no metric calibration or physical A/B mapping.

One SQL window row indexes the file hash, sample bounds, diagnostics, and candidate intervals. It does not add a SQL row for every sampled frame. A bounded rolling image buffer retains the first/last frame, the decoded frame closest to the requested midpoint, and start/end anchors for up to three configurations: at most nine composite frames and their seed crops. The endpoint/midpoint policy is versioned separately from vision checks. It supplies three temporal observations for clock/board consistency even when no house configuration passes; if fewer than three distinct frames were decoded, it keeps only those real frames. Midpoints retain original PTS, never a fabricated midpoint timestamp. Other images are discarded after analysis. Inspecting unretained pixels or applying a new image model requires decoding this short interval again; raw per-frame pixel measurements remain available in Parquet for later geometry work.

The API serves `GET /api/windows/WINDOW_ID/observations.parquet` only after checking its content hash and path. Releases include window manifests and anchor references; the local evidence/Parquet files need to accompany a backup. Repeated identical successful requests reuse their job. **Reanalyze this window** or CLI `--new-run` creates an explicit fresh run while retaining the old one. Detector, temporal method, profile, and source manifest changes also produce new job identities. Failed attempts publish no partial logical window, although already written content-addressed artifacts may remain in the bounded cache. A failed dense attempt currently decodes its small interval again on retry.

## Experimental persistence checks

`handle-configuration-persistence-v3` requires at least four distinct samples spanning 1.5 seconds. The complete candidate set must match by color and position against both the first and previous samples. Global crop motion, gaps, count/position/color changes, clipped candidates, large dark regions, blue-ring obstructions, or an unavailable ring reference split the run. An empty detection list is unknown visibility/detection, not an empty-house claim.

The dark-region check uses low-value, modest-saturation connected components larger than 1% of the crop, with a minimum extent. It flags possible obstruction. It is not a person detector: logos or granite clusters may also trigger it, and people can be missed. Its absence does not establish clear ice. These thresholds are experimental and are not calibrated probabilities or measured accuracy rates.

A real January pilot exposed a persistent person’s foot/clothing false positive under v1. The retained frame also contains a large dark foreground region; v2 abstains on such frames. The old proposed run remains visible with an earlier-version label. This is a development regression case, not held-out evidence of accuracy. Persistence alone cannot distinguish every broom, logo, garment, or stone.

Configuration proposals carry exact source times, anchor IDs, and YouTube links. They have no score, winner, physical stone identity, delivery number, or established end phase. Before automatic end scoring, add calibrated footprints, stronger visibility/detection models, direction/clearing and board reconciliation, and independently labeled evaluation across sheets and dates.


The v5 handle detector preserves rejected color/shape proposals in `hogline-dense-observations-v3` Parquet with a `rejection_reasons` list. The workbench distinguishes windows made with earlier detector versions even when the persistence method is unchanged. A detector upgrade does not overwrite prior window manifests or publish an accepted game state.

Four real ten-second windows (January Sheet 5, March Sheets 3, 4, and 6) were rerun with v5: 160 rows, 47 retained rejections, 51 worker seconds total. All files passed checksum and source-time checks. The persistence gate still abstained on all four intervals because of clipping/foreground/motion; a better handle detector alone does not establish a complete settled house.


## Brighter foreground and varying painted rings

`dark-and-blue-ring-obstruction-v2` adds an image-space cue for gray or brighter objects that interrupt the blue house ring. It fits the existing blue ellipse, computes blue-pixel support in one-percent radial bins, and finds the outermost continuous band of at least ten bins with 70% blue support. It trims the band edges before testing non-blue connected regions with the same 1%-area / 15%-extent thresholds as the dark-region gate. The painted width is measured per crop rather than assumed identical on every sheet. These are image priors, not a surveyed calibration.

The dense `hogline-dense-observations-v4` schema stores the fitted reference, measured band radii, visibility method, obstruction kind, bounding box, and area. The manifest pins the visibility method alongside detector, decoder, and persistence versions. Missing/unusable ring references cause persistence to abstain. The UI separately counts dark-region, ring-obstruction, and unavailable-reference samples; old window manifests remain unchanged and visibly carry earlier-version status.

Across 198 retained detailed overhead views from all eight sheets, reference fitting produced a usable blue-band candidate in each view. Thirty views triggered the darkness cue and eleven triggered the ring cue; categories overlap. Both anchors of the newly discovered gray-clothing failure now trigger the ring cue. These are development checks, not independent obstruction recall/precision. Synthetic cases cover narrow/wide painted rings, both 320- and 480-pixel crops, a small gray stone, a large bright-gray obstruction, and absent ring support.

A person entirely inside the inner white/green rings, blue clothing, a bad ellipse, glare, or an unfamiliar layout can still evade or confuse these checks. Stone clusters and painted markings can also trigger conservative abstention. Absence of a flag never establishes clear ice. The v5 handle detector still has the two garment false positives in the 19-view development dataset; the visibility change prevents the bad configuration proposal rather than claiming to fix those detections.

The v3 persistence / v2 visibility rerun decoded four ten-second windows on Sheets 2, 4 (both recordings), and 6: 160 rows in 31.4 worker seconds. The gray-clothing interval flagged blue-ring obstruction in 19 of 20 top-house samples and produced no persistent configuration. The earlier four-candidate proposal remains in history. Artifact checksums, manifest versions, source time bounds, and the browser comparison were verified.

The v2 retention policy was rerun on the same Sheet 2/6 intervals used for the automatic-campaign check. It reused both coarse scans, retained three temporal frames for each window (plus one distinct house-configuration anchor on Sheet 6), and read the two new midpoint frames. The complete follow-up used 22.59 worker seconds and 3.06 MiB of new retained data. Existing endpoint evidence and OCR outputs remained reusable.


The October 28 Sheet 3 check at 5400–5412 seconds selected 48 quarter-second samples on the source grid. It used 9,527,146 evidence bytes and 19.60 worker seconds. The resulting 21 body fragments made 12 exact-overlap links to retained fragments; nine ambiguous overlaps remained separate. This is a bounded overlap-link check, not a count of distinct people or validated throwers. Older detector versions lacking frame hashes remain independently indexed.
